## 一、AB 平台：从"平台上岸"到"科学实验"

### 核心转向

AB 平台不再只是"把实验跑起来"，而是帮助业务把实验**设计得更准、成本更低、结论更可信、策略更可落地**。

标题里的"从平台上岸到科学实验"，分三层含义：

**第一层：以前的核心问题是工具可用性（"平台上岸"阶段）**

- 实验准不准？
- 平台好不好用？
- 业务会不会配实验？
- 查询、开实验、看结果是不是顺？

这是"平台上岸"阶段，重点是把基础能力补齐，让业务能稳定使用 AB 实验系统。

**第二层：降低 MDE，让实验更有把握**

左边讲"实验更科学 - 降 MDE 更置信"，包括三个方法：

1. **流量计算器**：提前预估实验最小流量
   - 解决"实验还没开始，就知道大概要多少流量才够"
   - 让实验从"拍脑袋开"变成"开之前先算账"

2. **CUPED / CUPAC**：通用降低指标 MDE 50%+
   - 利用实验前的历史信息降低指标波动
   - 控制用户天然差异，降低指标方差，提升统计功效
   - 让小效果更容易被检测出来

3. **Capping 方法产品化**：直播营收场景落地
   - 限制极端值影响（直播打赏、营收等长尾分布指标）
   - 降低指标波动，让结论更稳

**第三层：HTE 异质性分析，归因更准确**

HTE = Heterogeneous Treatment Effect（异质性处理效应）：同一策略对不同人群的效果不一样。

两类方法：
1. **"因果树"**：10 维以内，可解释性好 — 找出哪些子人群策略效果更好
2. **"深度建模"**：500 维，通过深度学习找"策略做功人群"

> 进展：65 个深度建模任务，4 个实验已经基于挖掘策略重开

**最终结论**：

> AB 实验平台正在从基础工具，升级成业务增长的科学决策系统。不是只告诉你"实验组比对照组涨了多少"，而是进一步回答：设计有没有足够把握、指标波动能不能降低、结果是否被极端值污染、策略到底对谁有效、哪些人群值得重新开实验验证。

## 二、MDE 与 HTE 概念深度解析

### MDE = Minimum Detectable Effect（最小可检测效果）

在给定实验流量、周期、指标波动、显著性水平和统计功效的前提下，实验**至少要产生多大的真实提升，才有较大概率被检测出来**。

**MDE 的决定因素**：

| 因素 | 影响 |
|------|------|
| 样本量/流量 | 流量越大，MDE 越低（越灵敏） |
| 指标波动性 | 指标越稳定，MDE 越低 |
| 显著性水平 α | α 越严格（如 0.01），MDE 越高 |
| 统计功效 Power | Power 越高，MDE 越高 |
| 实验分流比例 | 50/50 最有效率，灰度实验灵敏度差 |

**MDE 为何重要**：

1. **避免"实验开了，但注定看不出来"** — 样本量不足是实验失败的主要原因
2. **帮助决定实验需要多少流量和周期** — 流量计算器的价值
3. **帮助解释"不显著"的实验结果** — 区分"策略没效果"和"实验检测不出来"
4. **帮助降低实验成本** — 通过 CUPED/Capping 等手段可大幅降低 MDE

**降低 MDE 的方法**：增加流量、延长时间、选更稳定的指标、使用 CUPED/CUPAC、对极端值做 Capping、优化分流比例、聚焦更可能受影响的人群。

### HTE = Heterogeneous Treatment Effect（异质性处理效应）

同一个实验策略，**对不同用户群体的影响是不一样的**。

**HTE 的典型场景**（以短视频推荐策略为例）：

整体播放时长 +0.3%（不显著），但 HTE 分析后发现：
- 新用户播放时长 +3%
- 老用户播放时长 -0.5%
- 低活用户 +2%
- 三四线城市用户 +1.5%

**平均值掩盖了真相**。

**HTE 的四大价值**：

1. **解决"平均值掩盖真相"** — ATE（平均处理效应）不能指导精细化策略
2. **帮助找到"策略做功人群"** — 识别真正被策略影响、产生正向变化的人群，定向投放，提升 ROI
3. **避免策略伤害某些人群** — 发现局部负向效果，支持推全决策
4. **支持策略精细化和二次实验** — 标准流程：全量实验 → HTE 分析 → 新策略假设 → 针对高潜人群重开实验 → 定向上线

### MDE 与 HTE 的关系

| 阶段 | 关注指标 | 核心问题 |
|------|---------|---------|
| 实验前 | MDE | 实验设计够不够敏感？流量够不够？ |
| 实验后 | HTE | 策略到底对谁有效？应该怎么精细化应用？ |

> 没有 MDE，AB 实验容易变成"跑完才发现看不出来"。没有 HTE，AB 实验容易变成"只看平均值，错过真正有效的人群"。

**一句话概括**：
> **MDE 决定实验有没有能力发现效果，HTE 决定实验结果能不能转化为精细化策略。**

## 三、数据人才形态演进：从"数据 BP"到"数据 FDE"

### 背景判断

1. **AI 技术驱动**：Agentic 架构升级、LLM 知识管理、取数准确度提升，泛化能力大幅增强
2. **需求结构变化**：基础类需求被业务自助化工具承接，数据人才需聚焦更深层业务理解和决策支持
3. **数据基座成熟**：24 年统一指标口径 → 25 年沉淀业务知识资产 → 26 年在 AI 基座上做算法
4. **行业共识方向**：字节、阿里、Palantir 等公司都在推动类似的数据组织升级

### 传统数据人才

- **DE（数据工程/开发）**：ETL 开发、数仓分层、SLA 保障、数据治理、标签体系
- **DPM（数据产品/项目管理）**：指标体系、看板产品、AB 实验设计、业务诊断、数据洞察

问题：DE 偏工程实现，DPM 偏业务分析，分工容易割裂。

### 数据 FDE 是什么

**FDE = Forward Deployed Engineer（前线部署工程师）**

深入业务现场，直接面向业务问题，完成从数据建设到智能应用落地的一体化角色。

三类数据 FDE：

**第一类：数据应用 FDE**
- 重点：夯实日常数据支撑底座，主推 AI 驱动的数据策略应用
- 核心变化：从"给业务交付数据"变成"给业务交付数据应用"（经营分析应用、智能诊断工具、策略推荐系统、面向业务的 Agent 工具）

**第二类：数据内容建设 FDE**
- 重点：数据语义建设 + AI 原生数据架构
- 关键能力：大模型字典、业务知识图谱、口径统一、AI 原生数据架构
- 本质：**数据语义层和业务知识资产的建设者**

**第三类：数据工程架构 FDE**
- 重点：具备数据工程架构能力，承接底层数据工程与架构建设
- 包括：数据工程架构、数据服务能力、数据平台能力、AI 时代的数据治理和资产管理

### 四个工作层级

| 层级 | 说明 |
|------|------|
| 初级阶段 | 传统分工明显：DE 写 SQL，DPM 做原型 |
| 执行层 | AI Agent 自动化完成标准化交付，FDE 设计 Agent 工作流 |
| 协同层 | 设计 Agent 自动取数、校验口径、生成分析初稿的协作机制 |
| 认知层 | 定义业务问题、设计数据策略、验证业务价值、形成可复用方法论 |

**核心等式**：

> **数据 FDE = 数据 FDE 开发 + DE 做 DPM 的事**

**AI 时代，数据人的真正价值**不在"会不会写 SQL"，而在于能不能把业务问题翻译成数据问题，再把数据结果转化成业务动作。

**一句话概括**：
> **数据 FDE 的本质，是让数据人才从"业务支持者"升级为"AI 驱动的数据作战单元"。**

## 四、MyFlicker 产品路线图解析

### 五阶段演进路线

| 阶段 | 时间 | 产品/定位 | 核心价值 |
|------|------|-----------|---------|
| 阶段一 | 2025 年 | AI × 研发工具（KwaiPilot/KATE） | 工具化、点状提效，聚焦技术人员 |
| 阶段二 | 2026 Q1 | AI × 开发人员（CodeFlicker） | 让开发人员真正用 AI 开发，端到端承担部分需求 |
| 阶段三 | 2026 Q2 | AI × 所有人（MyFlicker 1.0） | Code 能力泛化，横向扩展到全岗位 |
| 阶段四 | 2026 Q3 | AI × 团队（MyFlicker 2.0） | 各团队经验和能力 AI 化 |
| 阶段五 | 2026 Q4-2027 | AI × 组织（MyFlicker 3.0） | 汇聚所有团队 AI 能力，构建组织大脑 |

### 三代产品，两次认知跃迁

**第一代：KwaiPilot — 代码补全工具（AI 角色：工具）**
- 定位：代码补全
- 能力：代码搜索、智能问答、一键生成、调试助手
- 解决：写代码时能不能更快一点？

**第二代：CodeFlicker — AI 工程师（AI 角色：工程师）**
- 定位：并行、主动、闭环、进化
- 执行链路：感知 → 思考 → 行动 → 复盘
- 解决：一个研发任务能不能让 AI 独立承担一部分？

**第三代：MyFlicker — 全员工作伙伴（AI 角色：伙伴）**
- 定位：跨会话记忆 + 全员工作伙伴
- 核心能力：
  - **记忆**：长期记忆、项目记忆、偏好记忆（让 AI 从"临时工"变为"长期协作者"）
  - **技能**：覆盖编程实现、数据分析、设计生成、运营客服、知识管理等全员场景
  - **持续执行**：提交目标 → 自主规划 → 持续执行 → 结果交付

### MyFlicker 的四类核心资产（护城河）

1. **记忆资产**：个人记忆、项目记忆、偏好记忆
2. **技能资产（Skill）**：专家经验、工作流、工具调用封装
3. **知识资产**：公司知识库、团队知识、领域知识
4. **工具资产**：CLI 化、平台化、AgentOS

### 底层支撑体系

| 层次 | 演进方向 |
|------|---------|
| 能力层 | CodeAgent → 通用 Agent → 垂直 Agent → 团队专家 Agent → 组织级 Agent |
| 资产层 | 公司级研发 Skill → 公司级通用 Skill → 各团队专家 Skill → 各领域知识 |
| 基建层 | 公司内部研发工具 → 公司内通用平台 CLI 化 → 各业务平台 CLI 化 |
| 制度层 | 成本分摊制 → Token 经济学（AI 成本变为员工 Token 配额） |
| 组织层 | 研发效能中心 → AI 生产力中心 |

### 评价体系升级

从"工具使用率"到"AI ROI"：

- 过去看：有多少人用了、调用了多少次
- 未来看：节省多少人力、提升多少交付效率、降低多少沟通成本、每消耗一个 Token 带来多少业务价值

**这是 AI 提效从"热闹阶段"进入"经营阶段"的标志。**

### 最核心洞察

> **MyFlicker 的真正价值，不是"让每个人多一个 AI 工具"，而是"让每个人、每个团队、每个组织都拥有可积累、可执行、可复用的 AI 能力"。**
>
> 工具用完就结束，伙伴会记得、会成长、会接着干。

## 五、关键术语汇总

| 术语 | 全称 | 说明 |
|------|------|------|
| MDE | Minimum Detectable Effect | 最小可检测效果，衡量实验灵敏度 |
| HTE | Heterogeneous Treatment Effect | 异质性处理效应，衡量策略对不同人群的差异效果 |
| ATE | Average Treatment Effect | 平均处理效应，AB 实验默认关注的整体效果 |
| CUPED | Controlled Experiment using Pre-Experiment Data | 利用实验前历史数据降低指标方差的方法 |
| CUPAC | - | CUPED 的扩展版本 |
| Capping | - | 对极端值做截断/限制，降低长尾分布指标的噪声 |
| FDE | Forward Deployed Engineer | 前线部署工程师，深入业务现场的数据人才形态 |
| DE | Data Engineer | 数据工程师 |
| DPM | Data Product Manager | 数据产品经理 |
| AgentOS | - | AI Agent 的操作系统基础设施 |
| Skill | - | 封装专家经验和工作流的 AI 可调用能力单元 |
