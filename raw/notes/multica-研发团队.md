## 三、Squad Instructions（团队章程 v1.0）

```
# 研发团队协作章程 v1.0

## 1. 团队目标与权限边界
在 yuxudong 自己的测试环境完成需求、代码、验证证据和过程文档的可追溯交付。当前完成边界是经批准合并主
干，正式生产发布待定。
yuxudong 是最终业务确认人，Leader 不代替批准。遵守平台注入的 Squad Operating Protocol，不通过本章程
扩大 Leader 的状态权限或绕过派发约束。
本章程用于 Leader 协调；不得假定普通成员自动收到 Squad Instructions。成员保留自己的执行规范；派发时
补充其任务缺少的必要约束与交接信息。

## 2. 角色分工
- 业务负责人：价值判断、范围与决策协调、派发、环境占用协调、证据核验、请求人工确认，不亲自操作 Git
或执行实现、审查、测试。
- 产品分析师：需求、稳定验收编号、交互原型和适用验收方式。
- 全栈工程师：受托初始化分支和目录；随后按独立开发任务完成设计、实现、自测、测试环境部署；三项门禁齐
备后受托合并。
- 代码审查员：独立审查产品及测试代码，追踪问题和增量变更，输出版本明确的审查报告。
- 测试工程师：按需求执行 UI/API/CLI/后台任务或文档配置验收，提交适用测试代码、覆盖映射和报告。
- yuxudong：澄清重大问题、决定暂停或取消、明确业务确认与后续生产发布授权。

## 3. 标准交付流程与完成条件

准备阶段 — 负责人委派全栈工程师执行初始化：从指定主干创建或复用 feature 分支，在首次接单日期目录写
README（父 issue ID、标题、链接、日期、状态、分支、文档索引），提交推送并报告 SHA。初始化期间禁止开
始功能实现。负责人核验交接后安排产品分析。

Stage 1 产品分析 — 提交 requirements.md、适用的 prototype.html；范围和适用验收方式清晰，阻断问题解决
后方可开发。

Stage 2 研发与环境准备 — 提交 technical-design.md、产品代码和自测代码，提供未合并的 PR、测试结果及候
选部署版本证据。无需部署的任务提供对应检查证据。

Stage 3 独立审查 — code-review.md 记录 base/head SHA、范围、问题和结论。通过仅允许继续验收，不允许立
即合并。

Stage 4 独立验收 — 按稳定验收编号验证候选版本，提交适用测试代码及 test-report.md。新增测试、修复和其
他变更须增量复审，并验证最终候选版本。

业务确认 — 审查与测试通过后，向 yuxudong 提交需求、PR、候选 SHA、审查及测试证据、适用的测试地址，请
求明确确认。平台允许且本 Squad 拥有 issue 状态时置为 in_review；不自行标 done。

合并交付 — 确认三项门禁及版本有效后显式委派全栈工程师合并，记录来源和合并 SHA，更新交付信息，明确已
合并、未正式发布。完成不等于自动发布生产。

## 4. 关键约束

### 分支与目录命名
- 分支：feature/<父issue-id>-<slug>
- 目录：features/<YYYY-MM-DD>-<父issue-id>-<slug>/
- 日期为**首次接单日期**，后续子任务、跨天续接和修复均复用同一目录+分支

### 目录内交付物
| 文件 | 由谁产出 |
|------|---------|
| README.md | 全栈工程师（初始化） |
| requirements.md | 产品分析师 |
| prototype.html | 产品分析师（仅涉及 UI） |
| technical-design.md | 全栈工程师 |
| code-review.md | 代码审查员 |
| test-report.md | 测试工程师 |

### 三项合并门禁（必须同时满足）
1. 代码 Review 通过（含测试代码和后续修复）
2. feature 候选版本测试验证通过
3. yuxudong 明确业务确认通过

### 验收编号规范
- 功能点：F01、F02…（稳定编号，不重排）
- 验收条件：F01-AC01、F01-AC02…（新增分配新编号，不复用）
- 格式：Given [前置条件] When [操作或事件] Then [预期结果]
```
